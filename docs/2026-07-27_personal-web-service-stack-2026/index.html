個人的Webサービスを作るときの構成 2026

個人開発でWebサービスを作るとき、静的サイトかサーバーが必要か、DB・ストレージ・メール配信・認証・決済をどう選ぶか。要件別の判断フローと、その背景にある「なぜその選択肢なのか」を整理する教材です。

対象
個人開発でWebサービスを作りたい、技術選定の考え方を知りたい方
作成日
2026-07-27
元投稿
個人的Webサービスを作るときの構成 2026（catnose, X）

この教材で学べること

要件別の技術選定フロー

静的サイト・サーバーあり・DB・ストレージ・メール配信それぞれの選び方の判断軸を学びます。

各選択肢が選ばれる理由

単なるツール名の暗記ではなく、コスト・規模・運用の手間という観点から「なぜその選択肢か」を理解します。

自分のサービスへの当てはめ方

このフローチャートを自分が作りたいサービスにどう適用するかの手順を扱います。

前提知識の確認

  • Webサービスにはフロントエンド・サーバー（バックエンド）・データベース・ストレージといった構成要素があることを知っている
  • 「静的サイト」と「サーバーが必要な動的サイト」の違いをおおまかにイメージできる
  • AWS・Google Cloud・Cloudflareといったクラウドサービスの名前を聞いたことがある

学習ロードマップ

  1. Phase 1 静的に作れるサイトの選び方を理解する

    1ページの簡単なページから、Astro・Next.js Static Export・簡単なAPIまでの選び方を確認します。

  2. Phase 2 サーバーが必要な場合の選び方を理解する

    規模とコスト・スピードのトレードオフから、TanStack Start・Vercel・OpenNextの使い分けを確認します。

  3. Phase 3 DB・ストレージの選び方を理解する

    Cloudflare系・Postgres系それぞれの選択肢と、コストとリスクのトレードオフを確認します。

  4. Phase 4 メール配信・認証・決済・アクセス制御を整理する

    送信量に応じたメール配信サービスの選び方と、その他の実務的な要素を確認します。

  5. Phase 5 複雑な要件とAIへの相談という締めくくりを理解する

    個人開発の範囲を超えるビジネス要件でのGoogle Cloud活用と、フローチャートの限界を確認します。

Concept 1

静的に作れるサイトの選び方

サーバー側の処理がほとんど要らないサービスは、静的サイトとしてCloudflareに置くのが基本方針です。複雑さのレベルによって選ぶツールが変わります。

要件 選択肢 選ぶ理由
1ページだけの簡単なページ htmlファイルを書いてCloudflareに置く フレームワークを導入する必要すらない、最小構成
単純な静的ビルド React + Vite ビルド設定がシンプルで、素早く立ち上げられる
ちょい複雑 Next.jsでStatic Export ページ数が多い・ルーティングが複雑でも、サーバーなしでビルドし切れる
記事っぽいコンテンツ中心 Astro コンテンツ中心のサイトに特化しており、パフォーマンスが出しやすい
ちょっとしたAPIが必要 Cloudflare Workersにエンドポイントを生やす、またはHonoを使う 静的サイトの構成を保ったまま、部分的にサーバー処理だけ追加できる

具体例

個人のポートフォリオサイトであれば「Next.jsでStatic Export」で十分ですが、「お問い合わせフォームだけサーバー側で処理したい」という場合、サイト全体をサーバーが必要な構成に切り替える必要はなく、そのフォーム送信だけをCloudflare WorkersやHonoで作った小さなAPIエンドポイントに任せる、という部分的な使い方ができます。

判断の軸: 「ページの複雑さ」と「サーバー処理がどれだけ必要か」を分けて考える。サーバー処理が一部だけなら、サイト全体を動的にする前に、Workers/Honoでの部分的なAPI追加を検討する。

理解チェック

個人ブログを作る場合、「単純なReact + Vite」ではなく「Astro」が候補に挙がる理由を、記事コンテンツ中心のサイトという特性から説明してください。

Concept 2

サーバーが必要な場合の選び方

ログイン機能やリアルタイム性の高い処理など、静的ビルドだけでは対応できない場合は、サーバーが必要な構成を選びます。ここでは「規模」と「コスト対スピード」のトレードオフが判断軸になります。

要件 選択肢 選ぶ理由
小規模〜中規模 TanStack Start on CF Workers Cloudflareの環境で完結し、コストを抑えつつサーバー機能を持てる
中〜大規模。最短で出したい Next.js on Vercel Next.jsとVercelの組み合わせは情報・実績が豊富で、開発速度を優先できる
中規模でコスト削減したい（苦しむ覚悟がある） OpenNext on CF Workers Next.jsの機能を保ちながらCloudflare Workers上で動かせるが、設定の複雑さを受け入れる必要がある

具体例：OpenNextの位置づけ

@opennextjs/cloudflareというアダプタは、Next.jsのビルド出力をCloudflare Workersで動く形式に変換します。Node.js互換フラグ（nodejs_compat）の有効化など、Vercelにそのままデプロイする場合と比べて設定項目が増えるため、「苦しむ覚悟がある」という注記がされているのは、コスト削減と引き換えに運用の複雑さを引き受ける必要があることを示しています。

判断の軸: 「開発・運用に割ける時間」と「コスト」のどちらを優先するかで選択肢が変わる。最短で出したいならVercel、コストを抑えたいがCloudflareの流儀に慣れているならOpenNext、という整理になる。

理解チェック

「小規模〜中規模」ではTanStack Start on CF Workersが候補になるのに対し、「中規模でコスト削減したい」場合はOpenNextが候補になっています。この2つの違いは何によって生まれると考えられますか（フレームワークの選択とデプロイ環境の関係から考えてください）。

Concept 3

DBの選び方

データベースの選定では「Cloudflareで完結させたいか」「Postgres/MySQLが必要か」「コストをどこまでかけられるか」が主な判断軸です。

要件 選択肢 選ぶ理由
小〜中規模 & CF Workersを使う D1 / Durable Objects Cloudflareのエコシステム内で完結し、追加のインフラ管理が要らない
Cloudflare以外で小〜中規模 Turso SQLite系の軽量DBをマネージドで使え、Cloudflare以外の環境でも扱いやすい
Postgresを使いたいが安くしたい 国内向けならSupabase、それ以外ならNeon どちらもPostgres互換で低コストな選択肢。ただしNeonは2026年7月時点で東京リージョンがないため、国内向けサービスではレイテンシの観点でSupabaseが有利になりやすい
Postgres or MySQLを使いたい & コストは許容できる PlanetScale 2025年にPostgresサポートがGAになり、MySQL・Postgresどちらの互換性も選べる選択肢になった
判断の軸: Cloudflare Workersを使う前提ならまずD1/Durable Objectsを検討し、Postgres/MySQLが必須になった時点でSupabase・Neon・PlanetScaleへ選択肢を広げる、という順序で考えると整理しやすい。国内向けサービスではリージョン（レイテンシ）も判断材料になる。

理解チェック

国内向けのサービスでNeonよりSupabaseが候補に挙がりやすい理由を、リージョンの観点から説明してください。

Concept 4

ストレージの選び方

画像や添付ファイルなどのオブジェクトストレージは、「コスト」と「データが消えた場合の被害の大きさ」のバランスで選びます。

要件 選択肢 選ぶ理由
節約したい R2 エグレス（転送）費用がかからず、コストを抑えやすい
吹っ飛んだら詰む AWS S3 または GCS（バージョニング有効化） 実績のあるマネージドストレージで、バージョニングを有効にすることで誤削除・上書きからも復旧できる
節約したい & 吹っ飛んだら詰む R2 + 定期バックアップ（S3/GCSの最安ストレージクラス） 普段の運用コストはR2で抑えつつ、バックアップ先を別クラウドの安価なストレージクラスに置くことで、片方の障害・誤操作にも備えられる
判断の軸: 「壊れても許容できるデータか」を最初に問う。許容できないデータほど、単一のストレージ・単一のクラウドに依存しない構成（別クラウドへの定期バックアップ）を検討する。

理解チェック

「R2 + 定期バックアップ」という構成が、単に「R2だけ」や「S3だけ」と比べてどのようなリスクに備えられるようになっているか説明してください。

Concept 5

メール配信の選び方

メール配信サービスの選定は「送信量」と「既に使っているインフラ（Cloudflare Workersなど）」が主な判断軸です。

要件 選択肢 選ぶ理由
たくさん送る AWS SES 導入はやや手間だが、大量送信時の単価が安い
Cloudflare Workersを使っている Cloudflare Email Service Workersからネイティブなバインディング（env.EMAIL.send()）で送信でき、SPF/DKIM/DMARCも自動設定される。2026年4月にEmail Sending機能がパブリックベータ化された新しい選択肢
あんまり送らない Resend 少量の送信であれば、シンプルに導入・運用できる

SendGridが候補から外れた理由

Twilio SendGridは2025年5月27日から無料プランの提供終了を開始し、同年7月26日に完全終了しました。新規アカウントは60日間のトライアル後、有料プラン（月額19.95ドル〜）のみとなっています。個人開発の少量送信用途では、無料プランがなくなったことで相対的な魅力が下がり、Resendなど他の選択肢に置き換わったという経緯です。

判断の軸: 送信量が増えるほど単価の安さ（SES）が重要になり、送信量が少ないうちは導入の手軽さ（Resend、あるいはWorkersを使っているならCloudflare Email Service）を優先する。

理解チェック

すでにCloudflare Workersでサービスを構築している場合、Resendではなく Cloudflare Email Service を検討するメリットは何だと考えられますか（認証情報の管理という観点から考えてください）。

Concept 6

決済・認証・リアルタイム同期・限定公開

個人開発でよく必要になるその他の要素についても、定番の選択肢と検討の順序が示されています。

要件 選択肢 選ぶ理由
決済 Stripe 個人開発における決済の事実上の標準で、実績・ドキュメントが豊富
認証 BetterAuthを検討し、要件が合わなければ何かサービスを使う まず自前でコントロールしやすいライブラリを検討し、要件（ソーシャルログインの種類、規模など）に合わなければ認証専業サービスに切り替える、という順序
リアルタイム同期したい Cloudflare WorkersのDurable Objects 状態を持つWorkerとして、複数クライアント間のリアルタイム同期を実現できる
一部の人にだけ公開したい Cloudflare Zero Trust アプリ側に認証機能を作り込まなくても、アクセス制御をインフラ側で完結できる
判断の軸: 「アプリのコア機能ではない部分（認証・アクセス制御）」は、まず既存サービス・インフラ機能で済ませられないかを先に検討し、自前実装は最後の手段にする。

Concept 7

ビジネス要件が複雑な場合：Google Cloudの組み合わせ

個人開発の枠を超えて、ビジネス的な要件（複雑な業務ロジック、非同期処理、スケジュール実行など）が絡む場合は、単一のマネージドサービスの組み合わせではなく、Google Cloudの各サービスを組み合わせる方針が示されています。

具体例

Cloud Run（コンテナ実行）、Cloud SQL（リレーショナルDB）、Memorystore（キャッシュ）、Cloud Tasks（非同期タスクキュー）、Cloud Scheduler（定期実行）、Cloud Storage（オブジェクトストレージ）といった要素を組み合わせることで、個人開発向けの軽量な構成では対応しきれない、複雑な業務要件（例: 複数の非同期処理が絡む業務システム）に対応できます。

判断の軸: 「個人開発の延長で作れる複雑さ」を超えたら、無理に軽量な構成にこだわらず、フルマネージドなクラウドサービス群への切り替えを検討する。

全体の意思決定フロー早見表

要素 最初に検討すべき選択肢 次に検討する選択肢
サイトの種類 静的サイト（React+Vite/Next.js Static Export/Astro） サーバーが必要ならTanStack Start / Vercel / OpenNext
DB D1 / Durable Objects（Cloudflare前提） Postgres/MySQLが必要ならSupabase / Neon / PlanetScale
ストレージ R2 重要データはS3/GCS（バージョニング）や併用バックアップ
メール Resend（少量） 大量ならSES、Workers前提ならCloudflare Email Service
複雑さの限界を超えたら 個人開発向けマネージドサービスの組み合わせ Google Cloudの各サービスを組み合わせる構成

自分のサービスに当てはめる手順

  1. 作りたいサービスが「静的に作り切れるか」「ログイン・動的処理が必要か」を最初に判断する。
  2. 動的処理が必要な場合、規模（小規模〜大規模）と、開発スピード・コストのどちらを優先するかを決める。
  3. DBが必要な場合、Cloudflareで完結させたいか、Postgres/MySQLが必須かを判断する。国内向けサービスならリージョン（レイテンシ）も確認する。
  4. ストレージは、データが消えたときの被害の大きさから、単一クラウドで良いか、バックアップを併用すべきかを決める。
  5. メール配信・認証・決済・アクセス制御など、コア機能でない部分は既存サービスで済ませられないかを先に検討する。
  6. 個人開発の枠を超える複雑さが見えてきたら、無理をせずGoogle Cloudなどのフルマネージド構成への切り替えを検討する。

まとめ・次のステップ

個人Webサービスの技術選定は、「静的か動的か」「規模」「コスト対スピード」「データが消えたときの被害」という少数の判断軸の組み合わせで、多くのケースを整理できます。元投稿の各選択肢（Cloudflare Workers系、Postgres系DB、メール配信サービスなど）は、それぞれ特定の課題（コスト、レイテンシ、運用の手間）を解決するために選ばれており、単に「流行っているから」選ばれているわけではありません。

一方で元投稿の最後にもある通り、「結局サービスの内容によって変わる」というのも重要な指摘です。このフローチャートは出発点の目安として使い、実際に作りたいサービスの要件（想定ユーザー数、予算、開発に割ける時間、データの重要度など）に照らして、AIやドキュメントに相談しながら最終的な選択を調整することをおすすめします。次のステップとしては、自分が作りたいサービスを1つ思い浮かべ、このフローチャートに沿って「静的サイト／サーバー要否／DB／ストレージ／メール」をそれぞれ仮決めしてみることをおすすめします。
